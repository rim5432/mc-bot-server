> This file is the **mandatory specification** for any AI agent (and
> human collaborator) working in this repository. All code must comply
> with the rules here. When in conflict with another doc, this file
> takes precedence over reference notes; `doc/architecture/boundaries.md`
> and `doc/decisions/*.md` take precedence over this file for the
> contracts they freeze.
>
> Project goal: a **mechanical bot device** for Minecraft 1.20.1 (Forge)
> with a clean LLM-harness separation. The mod is the device layer; an
> external harness (LLM, programmatic driver, CLI, test rig) drives it
> through boundary D — see [§0.3](#03-boundaries-quick-reference).

### 0.2 Tool Rules (MANDATORY — search speed + build discipline)

- **Prefer `rg` (ripgrep)** for content search. `grep` is 100x slower
  on Windows. Fallback chain: `grep -rl`, then
  `findstr /s /i /m`. Never let a failed search block the task — try
  the next tool in the chain.
  - `rg -l "pattern" <path>` — list matching files
  - `rg "pattern" <path>` — show matches with context
  - `rg --files <path>` — list all files
- **Build / test / run via `python tool/mcbot_tool.py ...`**, never
  direct `./gradlew` or bare `gradle` — even if the wrapper is ever
  fixed — because a direct call bypasses the cross-process lock that
  every other agent relies on. The tool wraps the lock, hang-proof
  logging, and the correct gradle flags. Command essentials in
  §3.5 of this file; the full subcommand table lives in
  `tool/README.md`.
  - `python tool/mcbot_tool.py build compile`
  - `python tool/mcbot_tool.py test`
  - `python tool/mcbot_tool.py build runServer` (long-running; Ctrl+C)
  - `python tool/mcbot_tool.py status` / `log tail` / `lock status`
- **Concurrency etiquette**: everything that writes `build/`
  (compile / test / jar / build / clean / sync) serializes on the
  global `build` lock (`tool/.runtime/build.lock`); each long-running
  game task (`runClient` / `runServer` / `runGameTest` / `runData`)
  holds its own `run.<task>` lock, so a dedicated server and a dev
  client can be alive at the same time — they only read build
  outputs. A second caller of the SAME namespace fails fast with
  `BUSY: holder pid=...`; retry, or check holders with `lock status`
  (lists every namespace). Dead holder → just re-run (auto takeover)
  or `lock clear`. Never kill another agent's processes to grab the
  lock — it may hold unsaved work.
- **Long-running runs** hold their own `run.<task>` lock until MC
  exits. Verify with `build compile` / `jar` first; for background +
  live-log runs use the Start-Process pattern in `tool/README.md`.
  Compiling while a run is alive may fail on Windows file locks
  (the running JVM holds the moddev jars open) — stop the run or
  retry after it exits.
- **Read-only checks** (`tasks`, `deps`, `status`, `log *`, `lock
  status`, `proc list`, `doc list/check/touch/index/new`) do not need
  the lock and can be called freely.

### 0.4 Boundaries Quick Reference

The four boundaries are the only contract that matters. The full
contract lives in `doc/architecture/boundaries.md`; this section is
the at-a-glance for code review.

| ID | Sides | One-line rule | Full |
|---|---|---|---|
| **A** | Bot ↔ MC engine | `WorldView` is read-only, mockable, zero side effects. `Actor` emits intents, never self-computed physics. `core/` has zero MC imports. | [ADR-0002 §6](doc/decisions/0002-capability-model-task-arbiter.md) + [boundaries.md](doc/architecture/boundaries.md) |
| **B** | Process ↔ Behavior | Process is side-effect-free; output is `Directive{Goal, Overrides}`. Behavior monopolizes `Actor` via per-channel claims. Feedback closes via `ExecutionReport`. | [ADR-0002](doc/decisions/0002-capability-model-task-arbiter.md) + [ADR-0004 D3](doc/decisions/0004-tick-pipeline-actor-channels.md) |
| **C** | ReflexLayer ↔ Arbiter | Reflex ticks first, non-null reflex skips mission. Preemption carries `InterruptionContext`; resume revalidates world. Reflex never enters arbiter numerics. | [ADR-0003](doc/decisions/0003-reflex-layer-preemption.md) |
| **D** | Bot ↔ Harness | Command channel: `submit` / `cancel`. Event stream: `statusSnapshot(sinceEventId)`. State snapshot: `getState`. Bot is harness-blind. See [Boundary D protocol](doc/architecture/boundaries.md#boundary-d-protocol) for the six invariants. | [boundaries.md §D](doc/architecture/boundaries.md) + [disclosure-patterns.md](doc/reference/disclosure-patterns.md) |

**Rule of thumb**: if a code change seems to require opening a new ADR
or amending a frozen boundary, stop and write a workplan follow-up
item instead. The Stage 1 review is the only place that lifts the
freeze.

**Harness-side changes** (mc.py, skills, any boundary-D consumer)
review against [harness-interaction.md](doc/architecture/harness-interaction.md)
with the same severity as a boundary: its anti-patterns section is a
design-review reject list, not advice.

## 1. Code Style

Most of this section is adapted from the netcraft-rewrite project
conventions; only the **§1.4 contract marker** and the **formatting
exemption** differ. Wherever the two projects disagree, mc-bot-server
wins — netcraft-rewrite's rules are a starting point, not a mandate.

### 1.1 Package and Class Names

- Package prefix is `com.mcbot.mcbotserver.<module>`. `<module>` is a
  single level (`api`, `core`, `pathing`, `task`, `combat`, `event`,
  `state`, `boundary`, `tick`, `mixin`, `util`, …). **Never nest one
  module under another** — `com.mcbot.mcbotserver.core.api` is a
  namespace defect, not a legal package.
- The two halves of the layer split live in two top-level packages:
  - `com.mcbot.mcbotserver.api` — pure interfaces, DTOs, no MC imports.
    This is the layer a non-JVM harness could in principle bind to.
  - `com.mcbot.mcbotserver.core` — implementations; still zero MC
    imports. See §2.1.
- Class names describe behavior (`BotController`, `EventQueue`,
  `CompanionChunkLoader`), not pattern (`BotControllerImpl`,
  `EventQueueService`). Interfaces are nouns, impls are nouns that
  end in the implementation strategy when the strategy matters
  (`LoadedOnlyView` vs `CachedNavView` — same interface, different
  load semantics; see [numen-notes.md §7](doc/reference/numen-notes.md#7-the-cache-package-reveals-two-view-modes-that-must-not-be-conflated)).
- Mixin classes go under `com.mcbot.mcbotserver.mixin` (and
  `.mixin.accessor`, `.mixin.client`), matching the `package` field
  in the mixin JSON.

### 1.2 Naming

| Element | Rule | Good | Bad |
|---------|------|------|-----|
| Variables | Semantic; no decompile residue | `bot`, `event`, `tick` | `var0`, `param1` |
| Constants | `UPPER_SNAKE_CASE` | `DEFAULT_CAP`, `RESET_AT` | `defaultCap`, `ResetAt` |
| Fields (mutable) | `lowerCamelCase` | `currentTask` | `current_task` |
| Methods | `lowerCamelCase`, verb-led | `submit()`, `statusSnapshot(sinceEventId)` | `a()`, `m_262824_()` |
| Local variables | Short but meaningful; loop indices may use `i/j/k` | `holder`, `idx`, `bus` | `x1`, `temp` |

**Convention on records / sealed types**: data carriers use
`record` (`EventBatch`, `SubmitResult`); sum types use sealed
interface + permits (`SubmitResult { record Ok, record Rejected }`).
Don't reach for `enum` when the values carry different fields.

### 1.3 Imports

- **Explicit imports**; no wildcard `import x.*` unless there are
  20+ classes from the same package.
- Order: alphabetical, `java` / `javax` → third-party →
  `net.minecraft` / `net.minecraftforge` → `com.mcbot.mcbotserver.api`
  → `com.mcbot.mcbotserver.core`. The IDE's default sort is fine.
- `com.mcbot.mcbotserver.api.SubmitResult` and
  `com.mcbot.mcbotserver.McBotServer` are high-frequency references
  — keep them at the top of the import block.
- A class that imports anything from `net.minecraft.*` /
  `net.minecraftforge.*` is in the **impl** layer; it must not be
  under `com.mcbot.mcbotserver.api` (see §2.1).

### 1.4 Comments (English-only, intent-first)

Comments carry intent, constraints and invariants - what the next
editor must not break. Division of labor: code says what/how,
comments say why, Git records evolution. A comment that no longer
matches its code is a defect; fix it in the same commit as the
behavior change. If *what* needs a comment, refactor the code
instead. One concept, one word, everywhere - synonyms break global
search.

**1.4.1 Language - English only.** Every comment and Javadoc is
English. Exceptions are data, never comments: game-content strings
verbatim (`Component.literal("Stuck")`) and byte-fidelity registry
keys. Zero CJK characters in any repository `.md` file (see §0.3
for the markdown-side rule).

**1.4.2 Must-comment sites.**

- Class-level Javadoc: purpose plus the boundaries / ADRs the class
  implements, with the `contract: see ...` pointer.
- Every public / protected class, interface, enum, method, constant:
  Javadoc mandatory (package-private / private only when non-obvious).
  Tag order `@param` -> `@return` -> `@throws`; exactly one `@param`
  each; non-void needs `@return` (booleans state both meanings),
  void must not; nullability prose on every object param and return
  (`never null` / `may return null`); first sentence is a third-person
  summary ending in a period. Mechanics: `<p>` paragraphs,
  `{@code}` / `{@link}` references, `@apiNote` vs `@implSpec` for
  caller-vs-implementer when useful.
- Frozen-boundary write site: `// contract: see ADR-NNNN` or
  `// contract: see boundaries.md §X`.
- Method called from `BotController.onTick()`:
  `// invariant: see ADR-0005`.
- Off-thread entry or state crossing threads:
  `// runs on <thread>; do not access <off-thread state>`.
- Lifecycle / state-machine transition: one line naming the trigger.
- Stub: `// TODO <subsystem>: <what remains> (Ref: <issue>)` - a
  silent stub is a bug, an ownerless TODO is noise.
- Deliberate deviation from a reference design (Baritone / Numen):
  one line on what differs and why, so nobody "fixes" it back.

**1.4.3 Forbidden.** Restating the code; commented-out code (git is
the record); author / date graffiti; emoji, slang, unstandard
abbreviations; obvious getters and one-line overrides.

**1.4.3.1 Marker format** - the gate-scanned convention
(`BoundaryContractMarkerTest`, code-health H-R8: proves presence on
every src/main implementer of a boundary interface; its interface
inventory is pinned, growing it is a review checkpoint; review
judges quality):

```java
// contract: see boundaries.md §D (sync error path for structural failures)
public sealed interface SubmitResult {
    record Ok(String taskId) implements SubmitResult {}
    record Rejected(String reason) implements SubmitResult {}
}
```

Markers are contracts, not explanations: mandatory at every write
site that touches a frozen boundary, not just at the interface
declaration. A change that intentionally alters a frozen contract
updates the ADR or boundary doc FIRST, then the marker - never edit
the marker to dodge the doc.

**Style + density.** Constraints are imperative ("Must stay
byte-for-byte", "Do not call on the client thread"); lead words
separate roles at a glance (`Because` / `Must` / `Otherwise` for
rationale, `TODO`, `contract:`, `invariant:`); one comment per
statement; roughly one meaningful comment per 5-15 lines of logic,
denser only at contract points; a file whose comments exceed ~25%
of its lines is over-commented - tighten prose, never delete
contracts. Javadoc exists at class and public / protected API level
only. The English-only mandate is additionally review-enforced, and
scan-gated by the hygiene tests if drift appears.

### 1.5 Class Organization (for capability / event handler / boundary implementations)

Capability / event-handler / boundary-impl classes use a
**three-part layout**, separated by `// =====` dividers:

```java
public final class XxxCapability {
    // static fields (Capability instance + ResourceLocation ID)
    // @SubscribeEvent attach method
    // static get(Player) factory

    // ===== Interface =====
    public interface Xxx { ... }

    // ===== Default Implementation =====
    public static final class XxxImpl implements Xxx { ... }

    // ===== Provider / Adapter =====
    public static final class Provider implements ICapabilitySerializable<CompoundTag> { ... }
}
```

For boundary-D command/event/state channels, the equivalent split
keeps the channel's three shapes (request, response, snapshot) in
their own inner types; the outer class is just the channel surface
plus its three impls (mock, server-side, client-side).

### 1.6 Formatting

- 4-space indent, no tabs.
- Line width ≤ 120. **Review-only today** — no automated gate. Long
  type signatures and record-component lists are the typical
  exception; if a line genuinely cannot be wrapped, leave it and
  flag the next reviewer with a `// width-120: <reason>`.
- One statement per line; chain calls longer than 3 segments must
  break.
- `final` everywhere applicable (class, field, local variable,
  parameter), unless mutability is explicitly required. Records
  are implicitly final.
- Use `record` for pure data carriers (`EventBatch`,
  `SubmitResult.Ok`). Use sealed interface + permitted records for
  sum types.
- Trailing commas: required on multi-line argument lists and
  record-component lists (one element per line, last line ends
  with `,`).

## 2. Engineering Constraints (MC-specific, this project)

The four boundaries in §0.4 are the architecture-level constraints;
this section is the engineering-level constraints that follow from
them. Each is anchored in a specific ADR or `boundaries.md` section;
the anchor is the source of truth, not this file.

### 2.1 `core/` has zero MC imports (per ADR-0002 §6 + boundaries A)

- `com.mcbot.mcbotserver.api.*` is the layer a non-JVM harness could
  in principle bind to. It must contain only pure Java types, DTOs,
  and exceptions. `net.minecraft.*` and `net.minecraftforge.*` are
  forbidden imports.
- `com.mcbot.mcbotserver.core.*` is the offline-testable engine. It
  implements the API, but it still does not import MC types —
  `core/` reads and writes its own data shapes, and a separate
  adapter layer (the entity-binding spike in workplan Stage 1)
  bridges to MC.
- The **only** package that may import `net.minecraft.*` is the
  adapter layer, and that layer is not written in Stage 0. Until
  Stage 1 lands, MC imports are *literally* impossible — there is
  no code outside `McBotServer.java` (the mod entry point) that
  imports MC. When the adapter lands, it must live under
  `com.mcbot.mcbotserver.adapter` (or `mixin`, for mixin-only code),
  and a layer-1 test must assert "core/ + api/ still zero MC
  imports".
- Why this matters: the offline unit tests in Stage 0 must run
  without a Minecraft runtime. If `core/` imports MC, those tests
  cannot run on a CI box without Forge, and the project's
  acceptance gate (per [workplan Stage 0 gate](doc/guide/workplan.md))
  cannot pass.

### 2.2 Off-thread safety (per ADR-0004 D1 + decision 17b)

- `WorldView` and `Actor` are called on the **server tick thread**.
  Anything that runs on a different thread (the future A* worker,
  per workplan Stage 2) must go through the `ViewMode` parameter
  reserved by decision 17b — a `SNAPSHOT` view is captured on the
  main thread and read off-thread; a `LIVE` view must be a
  server-thread-only facade that the worker calls back into via a
  `CompletableFuture` or equivalent.
- Every class that may run off-thread carries a Javadoc line and
  a `// runs on <thread>` comment at every public method entry
  (see §1.4.2).
- Off-thread state capture that crosses the main-thread / worker
  boundary is a single atomic reference or a `Long2ObjectMap` copy
  — never a shared mutable object.

### 2.3 Tick exception policy (per ADR-0005)

- `BotController.onTick()` wraps the full four-stage pipeline
  (reflex → arbiter → behaviors → actor.flush) in **one**
  try-catch. Catching narrower (per stage) leaves the seams
  uncaught, which is where the original problem lives.
- On any caught `RuntimeException`:
  1. Latch `crashed = true` (sticky until harness reset).
  2. Capture an `InterruptionContext` snapshot (tick, pose,
     active identity, exception class/message/stack).
  3. Call `Actor.clearAllIntents()` exactly once, before any
     report.
  4. Emit through **both** `EventOutbox` (primary) **and**
     `System.err` + disk file (fallback). Either succeeding is
     sufficient; both are best-effort.
- After latch, the bot runs **only** `MinimalReflex` (a hard-coded
  reflex with no dependency on `ThreatBlackboard`, the rule
  table, or any derived computation). `MinimalReflex` and the
  full `ReflexLayer` share no mutable state.
- Recovery: harness `reset` command fully clears the latch and
  the `crashCounter`; bot death + respawn clears the latch but
  **preserves** the `crashCounter` (the harness reads the counter
  to detect pathological crash rates).

### 2.4 WorldView is read-only; Actor is intents-only (per boundary A)

- `WorldView` methods are pure reads; they return data shapes
  (`BlockSnapshot`, `EntitySnapshot`, `CollisionShape`) and never
  have side effects. The single exception is `isLoaded(pos)`,
  which is itself a pure read.
- `Actor` methods are *intents*: `setMoveIntent(...)`,
  `setRotateIntent(...)`, etc. They do not compute physics.
  Vanilla player physics is the only thing that moves the
  body — see [numen-notes §4](doc/reference/numen-notes.md#4-inputdriver-is-the-smallest-possible-input-emulation)
  for the design we are copying.
- A method that mutates world state and is not on `Actor` is a
  boundary violation; rename it to something that makes the
  intent obvious (e.g. `requestDig` not `dig`).

### 2.5 Bot is harness-blind (per boundary D protocol §6)

- The bot knows **nothing** about: LLM presence, consumer count,
  polling interval, subscription model, MCP / HTTP / gRPC choice,
  prompt assembly, conversation history.
- The bot is a passive event producer; the harness is the active
  consumer.
- Code that would have to "know" any of the above to do its job
  is in the wrong package. Move it to the harness-side adapter
  (Stage 0 reference: `tool/mcbot_tool.py` will host the first
  reference harness).

### 2.6 Tick ordering is fixed (per ADR-0004 D1)

```
BotController.onTick() {
    reflexLayer.tick()          -> non-null directive skips everything below
    arbiter.executeProcesses()  -> directives for behaviors
    behaviors.tick(world, directives) -> ExecutionReports + Actor claims
    actor.flush()               -> resolve channel claims, emit intents
}
```

Reordering this is a boundary violation. The contract is per-tick
(one tick latency is accepted and documented).

## 3. Workflow

### 3.1 Stage 0/1/2 from workplan.md

`doc/guide/workplan.md` is the **authoritative** Stage 0/1/2
checklist. Every item carries a size (S/M/L/XL) and a dependency
annotation (`[dep: <other item>]`). The rules:

- Do not start an item before its blockers are checked off.
- An item is **done** when it ships with a layer-1 test (offline
  JUnit) that proves its contract, plus a layer-3 test (gametest)
  if the contract requires real engine. The Stage 0 gate enumerates
  the four required tests (ordering, resume-validation, exception,
  disclosure).
- A checked-off item may regress. If it does, un-check it and add
  a workplan follow-up entry at the bottom of the current stage.

### 3.2 Per-class implementation procedure

1. **Read the contract first.** If the class implements a boundary
   interface, read the matching `boundaries.md` section. If it
   implements a decision, read the matching ADR.
2. **Write the Javadoc skeleton before the body.** Class-level
   Javadoc with the contract pointer (§1.4.3.1); method-level
   Javadoc with `@param` /
   `@return` / `@throws`. This is the design surface; the body
   implements it.
3. **Write the failing layer-1 test.** For Stage 0 this is
   straightforward — the test is a JUnit class asserting the
   contract. For Stage 1+ the gametest lives in
   `src/test/java/.../gametest/` and runs against `runGameTestServer`.
4. **Implement to the test.** No more code than the test requires.
   The Stage 0 gate requires that the offline tests pass against
   mocks, not against MC.
5. **Run `python tool/mcbot_tool.py build compile` and
   `python tool/mcbot_tool.py test`.** No commit on red.
6. **Update the doc that covers the class.** If the class touches
   a boundary, the contract marker (§1.4.3.1) goes in the Javadoc
   *and* in the matching `boundaries.md` row. Then `doc check` and
   `doc touch <name>`.

### 3.3 Commit Convention (Conventional Commits)

Every commit message follows the **Conventional Commits** spec. The
Git history is the third leg of the code / comment / Git division
of labor: code says *what/how*, comments say *why*, Git answers
*when, who, and for which reason a line changed*.

#### 3.3.1 Message format

```text
<type>(<scope>): <subject>

<body>

<footer>
```

| Part | Rule |
|------|------|
| `type` (required) | `feat` (new feature) · `fix` (bug fix) · `docs` (documentation / comments only) · `style` (formatting, no logic) · `refactor` (neither feature nor fix) · `perf` (performance) · `test` (tests) · `chore` (build / tooling / deps, no `src`) · `revert` |
| `scope` (recommended) | The affected module or subsystem, e.g. `api`, `core`, `tick`, `boundary-d`, `event`, `javadoc`, `tool`, `agents`. One word, no path separators |
| `subject` (required) | Imperative mood, lowercase, no trailing period, ≤ 72 chars, readable in `git log --oneline` |
| `body` (optional) | WHY it changed and what differs from before; lines ≤ 72 chars so the terminal renders it cleanly |
| `footer` (optional) | `Closes #<issue>` / `Refs #<issue>`; `BREAKING CHANGE: <description + migration>` when the change is not backward compatible |

#### 3.3.2 Repo-specific mapping

- A comment / Javadoc-only round is `docs(javadoc)`, not `chore`.
- Javadoc that explains a fix belongs **inside** that fix commit
  (docs that describe a change travel with the change).
- Tooling, tests, and config land in `chore` / `test` commits,
  never inside `docs` or `fix` commits.
- A boundary change goes in a `refactor(boundary-<letter>)` commit
  and the matching `boundaries.md` row updates in the **same**
  commit; the change is incomplete otherwise.
- The build result line goes in the body, e.g.
  `BUILD: compileJava + 4 L1 tests green`.

#### 3.3.3 Hard rules

1. **Atomicity** — one commit does exactly one thing. Never bundle
   a bug fix with a refactor or a feature: rolling back the
   refactor would drag the fix with it.
2. **Every commit compiles and passes tests.** No WIP, no
   half-broken intermediate states on the main line. History must
   be switchable — `git checkout <hash>` must always yield a
   runnable tree. Verify with
   `python tool/mcbot_tool.py test` before committing.
3. **Clean main-line history.** Feature work happens on a branch;
   the main line receives one perfect squash-merged commit per
   concern via PR/MR. Solo local workflow: still write every
   commit to the spec — once pushed, history can no longer be
   rewritten.

### 3.4 Build commands

All build / test / run / doc commands are funnelled through the
tool. The two commands every session needs are:

```bash
# Verify the build before any commit
python tool/mcbot_tool.py build compile
python tool/mcbot_tool.py test

# Audit the doc system
python tool/mcbot_tool.py doc check
```

When in doubt about a build issue: `python tool/mcbot_tool.py
status` → `python tool/mcbot_tool.py log tail -n 100` → `python
tool/mcbot_tool.py log cat <task>` (in that order); the failure-
symptom table lives in `tool/README.md`.

### 3.5 Tool reference (`tool/mcbot_tool.py`)

Why the tool exists: direct gradle calls bypassed the cross-process
lock and failed un-debuggably. The tool adds self-locating gradle,
hang-proof realtime logs, a fail-fast cross-process build lock with
stale-PID takeover, and an auto log tail on failure. The four
commands every session needs:

```bash
python tool/mcbot_tool.py build compile   # verify before any commit
python tool/mcbot_tool.py test            # no commit on red
python tool/mcbot_tool.py status          # locks + live runs + docs health
python tool/mcbot_tool.py doc check       # doc rot audit (the gate)
```

Lock discipline: everything writing `build/` serializes on the
global lock; long-running `build runClient` / `runServer` hold
their own `run.<task>` lock until MC exits; a second caller of the
same namespace fails fast with `BUSY: holder pid=...`. Failure
triage order: `status` -> `log tail -n 100` -> `log cat <task>`;
still opaque -> snapshot and escalate to the coordinating agent.

**Full subcommand table, flag passthrough (`--`, `--cc`), failure-
symptom table, runtime artifacts: `tool/README.md`.**
